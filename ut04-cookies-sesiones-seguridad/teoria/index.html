1. EL PROBLEMA DEL ESTADO EN HTTP

En la UT1 se vio que HTTP es un protocolo sin estado (stateless): cada petición se procesa de forma independiente y, cuando el servidor termina de responder, olvida al cliente. Si pides tres páginas seguidas, para el servidor son tres desconocidos distintos.

Sin embargo, casi todas las aplicaciones web necesitan recordar cosas de un cliente concreto entre una petición y la siguiente:

  • Que ya has iniciado sesión y quién eres.
  • Qué productos has metido en el carrito.
  • En qué paso de un formulario largo te has quedado.
  • Tus preferencias: idioma, tema oscuro, número de resultados por página.

A ese conjunto de datos lo llamamos estado. Mantener el estado consiste en conseguir que los datos de un cliente viajen o se guarden de forma que la siguiente petición pueda recuperarlos.

1.1. Mecanismos para mantener el estado

Mecanismo Dónde se guardan los datos Cómo viajan Ventajas Inconvenientes
Parámetros en la URL (?paso=2) En el enlace En cada enlace o redirección Sencillo; se puede compartir y guardar en marcadores Se ven, quedan en el historial y hay que añadirlos a todos los enlaces
Campos ocultos (<input type="hidden">) En el formulario Al enviar el formulario No necesita nada especial Solo funciona de formulario en formulario; el usuario puede cambiarlos
Cookies En el navegador En la cabecera Cookie de cada petición Persisten días o meses; no ocupan el servidor Unos 4 KB por cookie; el usuario puede leerlas y modificarlas
Sesiones En el servidor Solo viaja un identificador (en una cookie) Los datos no salen del servidor; sin límite práctico de tamaño Ocupan recursos del servidor; caducan
Web Storage (localStorage) En el navegador No viajan: solo los lee JavaScript Hasta unos 5 MB; cómodo desde JavaScript El servidor no los ve; accesibles a cualquier script de la página
Base de datos En el servidor — (se asocia a un usuario identificado) Permanente y compartida entre dispositivos Necesita identificar antes al usuario (UT6)

Regla práctica

  • Lo que no importa que el usuario vea o cambie (idioma, tema), en una cookie.
  • Lo que sí importa (quién es, qué rol tiene, qué hay en su carrito), en la sesión.
  • Lo que tiene que durar siempre y verse desde cualquier dispositivo, en la base de datos.

2. COOKIES

Una cookie es un par nombre = valor que el servidor pide al navegador que guarde. A partir de ese momento, el navegador la devuelve automáticamente en todas las peticiones al mismo sitio, hasta que caduque.

2.1. Cómo funcionan: dos cabeceras

Todo ocurre en las cabeceras HTTP que estudiaste en la UT1:

 1. GET /index.php                               (primera visita: no hay cookie)
    ─────────────────────────────────────────►
 2. 200 OK
    Set-Cookie: idioma=es; Max-Age=2592000; Path=/; HttpOnly; SameSite=Lax
    ◄─────────────────────────────────────────
                                  (el navegador guarda la cookie)
 3. GET /productos.php
    Cookie: idioma=es                            (la envía él solo)
    ─────────────────────────────────────────►
  • El servidor crea o modifica una cookie con la cabecera de respuesta Set-Cookie.
  • El navegador la devuelve con la cabecera de petición Cookie.

2.2. Crear una cookie: setcookie()

En PHP 8 la forma recomendada es pasar las opciones en un array asociativo:

<?php
// Guarda el idioma preferido durante 30 días
setcookie('idioma', 'es', [
    'expires'  => time() + 60 * 60 * 24 * 30,  // marca de tiempo: ahora + 30 días
    'path'     => '/',                          // válida en todo el sitio
    'httponly' => true,                         // JavaScript no puede leerla
    'samesite' => 'Lax',                        // protege frente a CSRF (apartado 7)
]);
Opción Significado Valor habitual
expires Momento en que caduca (marca de tiempo Unix). Con 0 es una cookie de sesión: se borra al cerrar el navegador time() + segundos
path Ruta a partir de la cual se envía '/'
domain Dominio al que se envía. Si se omite, solo el dominio actual Vacío
secure Solo se envía por HTTPS true en producción
httponly No es accesible desde JavaScript (document.cookie) true
samesite Si se envía en peticiones que vienen de otros sitios: Strict, Lax o None 'Lax'

Antes de cualquier salida

setcookie() añade una cabecera a la respuesta, y las cabeceras van antes del cuerpo. Si ya has enviado algo (HTML, un echo, un espacio o una línea en blanco antes de <?php), PHP no puede añadirla y muestra el aviso:

Warning: Cannot modify header information - headers already sent by (output started at …)

Lo mismo ocurre con header() y session_start(). Coloca toda la lógica al principio del fichero, antes del <!DOCTYPE html>.

setcookie() codifica el valor como en una URL (los espacios, tildes y símbolos se convierten en %20, %C3%B3…) y $_COOKIE lo descodifica al leerlo, así que no tienes que preocuparte por ello.

2.3. Leer una cookie: $_COOKIE

Las cookies que envía el navegador llegan en la superglobal $_COOKIE:

<?php
$idioma = $_COOKIE['idioma'] ?? 'es';   // valor por defecto si no existe

La cookie nueva no está en $_COOKIE hasta la siguiente petición

$_COOKIE contiene lo que el navegador envió en esta petición. Si llamas a setcookie() y a continuación lees $_COOKIE, verás el valor anterior (o nada). Si necesitas el valor nuevo en la misma página, usa la variable que acabas de guardar.

<?php
// Contador de visitas: lee, incrementa y guarda
$visitas = (int) ($_COOKIE['visitas'] ?? 0) + 1;

setcookie('visitas', (string) $visitas, [
    'expires' => time() + 60 * 60 * 24 * 365,
    'path'    => '/',
]);

echo "Es tu visita número $visitas";   // usa $visitas, no $_COOKIE['visitas']

2.4. Modificar y borrar una cookie

  • Modificar: vuelve a llamar a setcookie() con el mismo nombre (y la misma path y domain) y el nuevo valor.
  • Borrar: no existe una función para borrar. Se le indica al navegador una fecha de caducidad en el pasado:
<?php
// Borra la cookie 'visitas'. La ruta debe ser la misma con la que se creó.
setcookie('visitas', '', [
    'expires' => time() - 3600,
    'path'    => '/',
]);
unset($_COOKIE['visitas']);   // para que el resto del script tampoco la vea

2.5. Guardar varios datos en una cookie

Una cookie solo guarda texto. Para guardar varios datos relacionados, convierte un array a JSON al guardarlo y vuelve a convertirlo al leerlo:

<?php
// Guardar
$preferencias = ['tema' => 'oscuro', 'letra' => 'grande'];
setcookie('preferencias', json_encode($preferencias), [
    'expires' => time() + 60 * 60 * 24 * 365,
    'path'    => '/',
    'httponly' => true,
    'samesite' => 'Lax',
]);

// Leer (en otra petición)
$datos = json_decode($_COOKIE['preferencias'] ?? '', true);
if (!is_array($datos)) {
    $datos = [];   // la cookie no existe o no es JSON válido
}

No uses unserialize() con datos del usuario

Verás código antiguo que guarda arrays con serialize() y los lee con unserialize(). Con una cookie manipulada, unserialize() puede crear objetos arbitrarios y llegar a ejecutar código en el servidor. Usa siempre JSON.

2.6. Las cookies no son de fiar

El usuario puede ver, cambiar o borrar sus cookies en cualquier momento desde las herramientas del navegador (apartado 8) o enviar las que quiera con curl. Por eso:

  1. Valida el valor de una cookie como si viniera de un formulario: tipo, rango y lista blanca (UT3).
  2. Escápalo con htmlspecialchars() si lo muestras.
  3. Nunca decidas permisos con una cookie: una cookie rol=admin la puede escribir cualquiera.
  4. Nunca guardes en una cookie contraseñas ni datos personales.
<?php
// Lista blanca: si la cookie trae un valor no previsto, se usa el de por defecto
$temas = ['claro', 'oscuro'];
$tema = $_COOKIE['tema'] ?? 'claro';
if (!in_array($tema, $temas, true)) {
    $tema = 'claro';
}
Ampliación: cookies firmadas

Si necesitas detectar que una cookie ha sido modificada, puedes firmarla: guarda junto al valor un código calculado con una clave secreta que solo conoce el servidor. Si el usuario cambia el valor, la firma ya no coincide.

<?php
const CLAVE_SECRETA = 'cámbiame-por-una-cadena-larga-y-aleatoria';

function firmar(string $valor): string
{
    return $valor . '|' . hash_hmac('sha256', $valor, CLAVE_SECRETA);
}

function verificar(string $cookie): ?string
{
    [$valor, $firma] = array_pad(explode('|', $cookie, 2), 2, '');
    $esperada = hash_hmac('sha256', $valor, CLAVE_SECRETA);
    return hash_equals($esperada, $firma) ? $valor : null;   // null si la han tocado
}

Firmar impide modificar, pero no oculta el valor. Los frameworks como CodeIgniter (UT5) ya hacen esto por ti.

2.7. Almacenamiento en el cliente desde JavaScript

Además de las cookies, el navegador ofrece el Web Storage, que se maneja desde JavaScript (lo estudias a fondo en Desarrollo Web en Entorno Cliente):

<script>
    // localStorage: dura hasta que se borre. sessionStorage: hasta cerrar la pestaña.
    localStorage.setItem('vista', 'cuadricula');
    const vista = localStorage.getItem('vista');   // 'cuadricula'
</script>
Cookie localStorage sessionStorage
¿Lo recibe el servidor? Sí, en cada petición No No
Tamaño Unos 4 KB por cookie Unos 5 MB por sitio Unos 5 MB por sitio
Duración La que fije expires Indefinida Hasta cerrar la pestaña
Accesible desde JavaScript Sí, salvo con HttpOnly Sí Sí

Úsalo para preferencias que solo afectan a la interfaz (abrir o cerrar un panel, vista en lista o en cuadrícula). Lo que tenga que conocer PHP va en una cookie o en la sesión.

3. SESIONES

Con una sesión, los datos se guardan en el servidor y al navegador solo se le entrega un identificador aleatorio, el ID de sesión. En cada petición, el navegador devuelve el ID y PHP recupera los datos que le corresponden.

 Navegador                                Servidor
 ─────────                                ────────
 Cookie: PHPSESSID=k3j9…   ───────►   session_start()
                                       busca el fichero sess_k3j9…
                                       y lo carga en $_SESSION
                                              │
                           ◄───────   tu script lee y cambia $_SESSION
                                       al terminar, PHP guarda $_SESSION
                                       en sess_k3j9…

El ID viaja en una cookie que, por defecto, se llama PHPSESSID. Los datos nunca salen del servidor: el usuario no puede ver ni cambiar lo que hay en $_SESSION.

3.1. Iniciar la sesión y usar $_SESSION

<?php
session_start();   // crea una sesión nueva o recupera la existente

// Escribir
$_SESSION['nombre'] = 'Lucía';
$_SESSION['carrito'] = ['P01' => 2, 'P07' => 1];

// Leer (en esta o en cualquier petición posterior)
$nombre = $_SESSION['nombre'] ?? 'invitado';

// Borrar un dato
unset($_SESSION['carrito']);
  • session_start() debe llamarse en cada página que use la sesión y antes de cualquier salida, porque puede enviar la cabecera Set-Cookie.
  • $_SESSION es un array normal: puedes guardar números, cadenas, arrays… Al terminar el script, PHP lo guarda solo.
  • A diferencia de $_COOKIE, los cambios en $_SESSION se ven inmediatamente.

Comprueba si la sesión ya está iniciada

Si incluyes ficheros que llaman a session_start(), puedes acabar llamándolo dos veces (y PHP avisa). Protégelo así:

<?php
if (session_status() !== PHP_SESSION_ACTIVE) {
    session_start();
}

3.2. Ejemplo: carrito de la compra

<?php
session_start();

// Productos disponibles (en la UT6 vendrán de una base de datos)
$catalogo = ['P01' => 'Teclado', 'P02' => 'Ratón', 'P03' => 'Monitor'];

// El carrito es un array: código del producto => unidades
$_SESSION['carrito'] ??= [];

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $codigo = $_POST['codigo'] ?? '';

    // Lista blanca: solo productos que existen
    if (array_key_exists($codigo, $catalogo)) {
        $_SESSION['carrito'][$codigo] = ($_SESSION['carrito'][$codigo] ?? 0) + 1;
    }

    // Patrón POST/Redirect/GET (UT3): al recargar no se vuelve a añadir
    header('Location: carrito.php');
    exit;
}

$unidades = array_sum($_SESSION['carrito']);

El operador ??= (PHP 7.4) asigna el valor solo si la clave no existe o es null.

3.3. Configurar la sesión

El comportamiento de las sesiones se controla con directivas de php.ini que empiezan por session.. Puedes cambiarlas para tu aplicación pasándolas a session_start() sin el prefijo:

<?php
session_start([
    'cookie_httponly' => true,    // JavaScript no puede leer el ID de sesión
    'cookie_samesite' => 'Lax',   // no se envía en formularios de otros sitios
    'cookie_secure'   => isset($_SERVER['HTTPS']),  // solo por HTTPS si lo hay
    'use_strict_mode' => true,    // rechaza ID inventados por el cliente
]);
Directiva Valor por defecto Qué hace
session.name PHPSESSID Nombre de la cookie
session.cookie_lifetime 0 Duración de la cookie; 0 = hasta cerrar el navegador
session.gc_maxlifetime 1440 (24 min) Segundos sin uso tras los que los datos pueden borrarse
session.cookie_httponly Desactivada Marca la cookie como HttpOnly
session.use_strict_mode 0 Si vale 1, no acepta un ID que el servidor no haya creado
session.save_path Depende del sistema Carpeta donde se guardan los ficheros sess_…

¿Dónde están mis sesiones?

Ejecuta php -i | grep session.save_path en la terminal (o busca session en la salida de phpinfo()) y abre esa carpeta: verás un fichero sess_ seguido del ID por cada sesión, con el contenido de $_SESSION en texto. Compara el nombre con el valor de la cookie PHPSESSID de tu navegador.

3.4. Caducidad por inactividad

session.gc_maxlifetime no garantiza que la sesión caduque a su hora: el recolector de basura de PHP se ejecuta de forma aleatoria, de vez en cuando. Si tu aplicación necesita cerrar la sesión tras un tiempo sin actividad (una intranet, un banco), contrólalo tú:

<?php
session_start();

const INACTIVIDAD_MAXIMA = 10 * 60;   // 10 minutos en segundos

if (isset($_SESSION['ultimo_acceso'])
    && time() - $_SESSION['ultimo_acceso'] > INACTIVIDAD_MAXIMA) {
    // Ha pasado demasiado tiempo: se cierra la sesión (apartado 3.5)
    cerrarSesion();
    header('Location: login.php?caducada=1');
    exit;
}

$_SESSION['ultimo_acceso'] = time();   // se renueva en cada petición

3.5. Cerrar la sesión por completo

Cerrar una sesión bien requiere tres pasos: vaciar los datos, borrar la cookie del navegador y eliminar el fichero del servidor.

<?php
function cerrarSesion(): void
{
    // 1. Vaciar los datos
    $_SESSION = [];

    // 2. Borrar la cookie del ID, con los mismos parámetros con que se creó
    $parametros = session_get_cookie_params();
    setcookie(session_name(), '', [
        'expires'  => time() - 3600,
        'path'     => $parametros['path'],
        'domain'   => $parametros['domain'],
        'secure'   => $parametros['secure'],
        'httponly' => $parametros['httponly'],
        'samesite' => $parametros['samesite'],
    ]);

    // 3. Destruir la sesión en el servidor
    session_destroy();
}

session_destroy() no vacía $_SESSION

session_destroy() borra el fichero del servidor, pero el array $_SESSION sigue lleno hasta que termina el script. Si solo llamas a session_destroy() y luego muestras la página, todavía verás al usuario «conectado». Por eso se vacía primero con $_SESSION = [].

3.6. Mensajes flash

En la UT3 aplicaste el patrón POST/Redirect/GET, pero no podías mostrar en la página de destino un mensaje como «Producto añadido». Con la sesión sí: se guarda el mensaje antes de redirigir y se borra en cuanto se muestra. Por eso se llama flash: aparece una sola vez.

<?php
// Guardar un mensaje para la siguiente petición
function flash(string $tipo, string $texto): void
{
    $_SESSION['flash'][] = ['tipo' => $tipo, 'texto' => $texto];
}

// Recuperar los mensajes y borrarlos
function obtenerFlash(): array
{
    $mensajes = $_SESSION['flash'] ?? [];
    unset($_SESSION['flash']);
    return $mensajes;
}

<?php foreach (obtenerFlash() as $m): ?>
    <div class="notification is-<?= $m['tipo'] ?>"><?= htmlspecialchars($m['texto']) ?></div>
<?php endforeach; ?>

3.7. Las sesiones se bloquean

Mientras un script tiene la sesión abierta, PHP bloquea su fichero: si el mismo usuario hace dos peticiones a la vez (dos pestañas, varias peticiones con Axios), la segunda espera a que termine la primera. En scripts que tardan (generar un informe, llamar a un servicio externo), llama a session_write_close() en cuanto termines de escribir en $_SESSION; podrás seguir leyéndola.

4. MECANISMOS DE AUTENTICACIÓN

4.1. Autenticación y autorización

Son dos preguntas distintas que conviene no confundir:

Pregunta Ejemplo Si falla
Autenticación ¿Quién eres? Usuario y contraseña correctos 401 Unauthorized o vuelta al login
Autorización ¿Qué puedes hacer? Solo el rol admin entra en el panel de administración 403 Forbidden

Primero se autentica (una vez, al iniciar sesión) y después se autoriza (en cada petición a una zona protegida).

4.2. Mecanismos disponibles

Mecanismo Cómo funciona Dónde se usa Ventajas Inconvenientes
HTTP Basic El navegador pide usuario y contraseña en un cuadro propio y los envía en cada petición en la cabecera Authorization Paneles internos, entornos de prueba Muy sencillo; lo implementa el propio servidor web Credenciales solo codificadas en Base64 (no cifradas): exige HTTPS. No hay botón de «cerrar sesión». Interfaz no personalizable
HTTP Digest Como Basic, pero envía un resumen (hash) en lugar de la contraseña Casi en desuso No envía la contraseña Algoritmos antiguos; poco soporte
Formulario y sesión El usuario rellena un formulario; si es correcto, se guarda su identidad en la sesión La mayoría de aplicaciones web Control total de la interfaz y del flujo; permite cerrar sesión Hay que programar bien la seguridad (apartados 5 a 7)
Tokens (Bearer, JWT) Tras identificarse, el cliente recibe un token que envía en la cabecera Authorization APIs REST y aplicaciones móviles (UT7) No necesita sesión en el servidor; sirve para cualquier cliente Revocar un token antes de que caduque es complicado

En esta unidad programas los dos primeros de la lista que se hacen con PHP puro: HTTP Basic y formulario y sesión. Los tokens los verás en la UT7.

4.3. Autenticación HTTP Basic

El intercambio es así:

 1. GET /panel.php
                    ◄── 401 Unauthorized
                        WWW-Authenticate: Basic realm="Panel interno"
    (el navegador muestra su cuadro de usuario y contraseña)
 2. GET /panel.php
    Authorization: Basic YW5hOkFuYSMyMDI2      ← "ana:Ana#2026" en Base64
                    ◄── 200 OK
    (a partir de aquí, el navegador repite la cabecera en cada petición)

PHP descodifica la cabecera y deja los datos en $_SERVER['PHP_AUTH_USER'] y $_SERVER['PHP_AUTH_PW']:

<?php
// Usuarios permitidos: nombre => hash de la contraseña (apartado 5)
$usuarios = [
    'ana' => '$2y$12$sY7v8Tbgz89e02xQN0uLDu6binsLw4HIf3O31VxJ6mwJZXEmqrsV.',
];

$usuario = $_SERVER['PHP_AUTH_USER'] ?? '';
$clave   = $_SERVER['PHP_AUTH_PW'] ?? '';

$valido = isset($usuarios[$usuario]) && password_verify($clave, $usuarios[$usuario]);

if (!$valido) {
    // Se pide al navegador que muestre el cuadro de credenciales
    header('WWW-Authenticate: Basic realm="Panel interno", charset="UTF-8"');
    http_response_code(401);
    echo 'Necesitas identificarte para ver esta página.';
    exit;
}

echo 'Bienvenida, ' . htmlspecialchars($usuario);

Base64 no es cifrado

Copia el valor de la cabecera Authorization desde las herramientas del navegador y escribe en la consola atob('YW5hOkFuYSMyMDI2'): obtienes el usuario y la contraseña. Basic solo es aceptable sobre HTTPS.

5. ALMACENAMIENTO SEGURO DE CONTRASEÑAS

Una aplicación nunca debe guardar las contraseñas tal cual. Si alguien roba el fichero o la base de datos, tendría las contraseñas de todos los usuarios, que además suelen repetirlas en otros sitios.

Lo que se guarda es un hash: el resultado de aplicar a la contraseña una función de un solo sentido. A partir del hash no se puede obtener la contraseña, pero sí comprobar si una contraseña coincide.

5.1. password_hash() y password_verify()

<?php
// Al dar de alta al usuario: se guarda el hash, nunca la contraseña
$hash = password_hash('Ana#2026', PASSWORD_DEFAULT);
// $2y$12$sY7v8Tbgz89e02xQN0uLDu6binsLw4HIf3O31VxJ6mwJZXEmqrsV.

// Al iniciar sesión: se comprueba la contraseña escrita contra el hash guardado
if (password_verify($_POST['clave'], $hash)) {
    // contraseña correcta
}

Un hash de password_hash() contiene todo lo necesario para comprobarlo:

$2y$12$sY7v8Tbgz89e02xQN0uLDu6binsLw4HIf3O31VxJ6mwJZXEmqrsV.
 │   │  └────────── sal ─────────┘└──────────── hash ──────────┘
 │   └─ coste: 2¹² iteraciones
 └─ algoritmo: bcrypt
  • La sal (salt) es un valor aleatorio distinto para cada hash. Por eso, si ejecutas password_hash() dos veces con la misma contraseña, obtienes hashes distintos, y los dos son válidos.
  • El coste hace el cálculo deliberadamente lento (unas décimas de segundo). Para un usuario no se nota; para un atacante que prueba millones de contraseñas, sí. En PHP 8.4 el coste por defecto de bcrypt es 12.
  • PASSWORD_DEFAULT usa el algoritmo que PHP considere más adecuado en cada versión. Como puede cambiar, la columna donde se guarde el hash debe admitir 255 caracteres.

Ni md5() ni sha1()

Son funciones rápidas, pensadas para comprobar ficheros, no contraseñas. Con una tarjeta gráfica se prueban miles de millones de contraseñas por segundo, y además existen tablas con los hashes de millones de contraseñas habituales. Tampoco se «cifra» la contraseña con una clave para poder descifrarla después: si la aplicación puede recuperarla, también puede hacerlo quien la robe.

5.2. Actualizar hashes antiguos

Si un día aumenta el coste por defecto o cambia el algoritmo, password_needs_rehash() te dice si un hash guardado está anticuado. El momento de rehacerlo es justo después de un inicio de sesión correcto, que es cuando tienes la contraseña en claro:

<?php
if (password_verify($clave, $hash) && password_needs_rehash($hash, PASSWORD_DEFAULT)) {
    $nuevoHash = password_hash($clave, PASSWORD_DEFAULT);
    // guardar $nuevoHash en lugar del anterior (en la UT6, con un UPDATE)
}

Generar un hash desde la terminal

Mientras no tengas base de datos, guardarás los usuarios en un array. Para obtener el hash de una contraseña, crea este pequeño script y ejecútalo desde la terminal (funciona igual en Xubuntu, Windows y macOS):

<?php
// crear-hash.php · Uso: php crear-hash.php "Contraseña#2026"
if (PHP_SAPI !== 'cli') {
    exit('Ejecuta este script desde la terminal.');   // no debe abrirse en el navegador
}
echo password_hash($argv[1] ?? '', PASSWORD_DEFAULT), PHP_EOL;

php crear-hash.php "Ana#2026"

6. INICIO DE SESIÓN CON FORMULARIO Y CONTROL DE ACCESO

Vamos a construir una pequeña aplicación con zona privada. Mientras no tengas base de datos (UT6), los usuarios se guardan en un fichero PHP que devuelve un array.

app/
├── datos/
│   └── usuarios.php      ← usuarios, hashes y roles
├── includes/
│   └── auth.php          ← funciones de sesión y control de acceso
├── login.php             ← formulario de inicio de sesión
├── privado.php           ← zona para cualquier usuario identificado
├── admin.php             ← zona solo para el rol admin
└── logout.php            ← cierre de sesión

6.1. Los usuarios

<?php
// datos/usuarios.php
// Cada usuario: nombre de usuario => datos. Las contraseñas están como hash.
return [
    'ana' => [
        'nombre' => 'Ana Pérez',
        'rol'    => 'usuario',
        'hash'   => '$2y$12$sY7v8Tbgz89e02xQN0uLDu6binsLw4HIf3O31VxJ6mwJZXEmqrsV.',
    ],
    'admin' => [
        'nombre' => 'Administración',
        'rol'    => 'admin',
        'hash'   => '$2y$12$zdpEX4D76gFFK3ndqjEgduengrdF4CpbBf32QUHSscP4GQRri6HSO',
    ],
];

Un fichero incluido con return devuelve ese valor: $usuarios = require __DIR__ . '/datos/usuarios.php';.

6.2. Las funciones comunes

<?php
// includes/auth.php: se incluye al principio de todas las páginas

// Inicia la sesión con una configuración segura (apartado 7)
if (session_status() !== PHP_SESSION_ACTIVE) {
    session_start([
        'cookie_httponly' => true,
        'cookie_samesite' => 'Lax',
        'use_strict_mode' => true,
    ]);
}

/** Escapa un texto para mostrarlo en HTML. */
function h(?string $texto): string
{
    return htmlspecialchars($texto ?? '', ENT_QUOTES, 'UTF-8');
}

/** Devuelve los datos del usuario identificado, o null si no hay nadie. */
function usuarioActual(): ?array
{
    return $_SESSION['usuario'] ?? null;
}

/** Si no hay nadie identificado, redirige al login y termina el script. */
function requiereLogin(): void
{
    if (usuarioActual() === null) {
        header('Location: login.php');
        exit;   // ¡imprescindible!
    }
}

/** Además de estar identificado, exige un rol concreto. */
function requiereRol(string $rol): void
{
    requiereLogin();
    if (usuarioActual()['rol'] !== $rol) {
        http_response_code(403);
        exit('403 · No tienes permiso para ver esta página.');
    }
}

exit después de redirigir

header('Location: …') solo añade una cabecera: el script sigue ejecutándose y envía el resto de la página. El navegador obedece la redirección y no la muestra, pero cualquiera que haga la petición con curl verá todo el contenido «protegido». Pon siempre exit; justo después.

6.3. El formulario de inicio de sesión

<?php
// login.php
require __DIR__ . '/includes/auth.php';
$usuarios = require __DIR__ . '/datos/usuarios.php';

$error = '';

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $login = trim($_POST['usuario'] ?? '');
    $clave = $_POST['clave'] ?? '';

    $datos = $usuarios[$login] ?? null;

    if ($datos !== null && password_verify($clave, $datos['hash'])) {
        // Nuevo ID de sesión al cambiar de privilegios (apartado 7.2)
        session_regenerate_id(true);

        // Se guarda lo necesario, nunca la contraseña ni el hash
        $_SESSION['usuario'] = [
            'login'  => $login,
            'nombre' => $datos['nombre'],
            'rol'    => $datos['rol'],
        ];

        header('Location: privado.php');
        exit;
    }

    // Mismo mensaje tanto si el usuario no existe como si la clave es incorrecta
    $error = 'Usuario o contraseña incorrectos.';
}
?>

    <div class="container" style="max-width: 400px;">
        <form method="post" class="box">

Fíjate en tres decisiones:

  1. El mensaje de error es el mismo en los dos casos. Si dijera «el usuario no existe», un atacante podría averiguar qué usuarios hay.
  2. El formulario conserva el usuario escrito, pero nunca la contraseña (UT3).
  3. En la sesión se guarda el rol, que viene de los datos del servidor, nunca de algo que envíe el cliente.

6.4. Las páginas protegidas

Proteger una página es una sola línea al principio:

<?php
// privado.php: cualquier usuario identificado
require __DIR__ . '/includes/auth.php';
requiereLogin();
$usuario = usuarioActual();
?>
<h1 class="title">Hola, <?= h($usuario['nombre']) ?></h1>
<?php if ($usuario['rol'] === 'admin'): ?>
    <a href="admin.php">Ir a administración</a>
<?php endif; ?>

<?php
// admin.php: solo el rol admin
require __DIR__ . '/includes/auth.php';
requiereRol('admin');

Que «Atrás» no muestre la página

Después de cerrar sesión, el botón Atrás del navegador puede mostrar una copia guardada de la página privada. Para evitarlo, envía en las páginas protegidas la cabecera header('Cache-Control: no-store');. Puedes ponerla dentro de requiereLogin().

Ocultar el enlace no es proteger

Que el enlace a admin.php solo aparezca para los administradores es una cuestión de interfaz. Cualquiera puede escribir la URL a mano. La protección real es requiereRol('admin') al principio de admin.php.

6.5. Cerrar la sesión

<?php
// logout.php
require __DIR__ . '/includes/auth.php';

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    cerrarSesion();   // función del apartado 3.5, guardada en auth.php
}
header('Location: login.php');
exit;

El botón de salir es un formulario POST, no un enlace. Así otra web no puede cerrar la sesión de tus usuarios con una simple imagen <img src="https://tusitio/logout.php">:

<form method="post" action="logout.php">
    <button class="button is-light">Cerrar sesión</button>
</form>

6.6. «Recordarme»

Muchas webs ofrecen mantener la sesión abierta durante semanas. Nunca se hace guardando el usuario y la contraseña en una cookie. La técnica correcta guarda en la cookie un token aleatorio (bin2hex(random_bytes(32))) y en la base de datos su hash, asociado al usuario y con fecha de caducidad. La retomarás cuando tengas base de datos. Lo que sí puedes hacer ya es recordar el nombre de usuario para rellenar el formulario.

7. SEGURIDAD EN LA GESTIÓN DEL ESTADO

Quien consigue el ID de sesión de otra persona es esa persona para tu aplicación. La mayoría de ataques de este apartado buscan eso, o hacer que el navegador de la víctima actúe por ella.

7.1. Robo de sesión (session hijacking)

El atacante obtiene el ID de sesión de la víctima: leyendo la cookie con un script inyectado (XSS), espiando una red wifi sin HTTPS o encontrándolo en una URL compartida.

Defensas: cookie de sesión con HttpOnly (los scripts no la leen) y Secure (solo viaja cifrada por HTTPS), escapar toda la salida para evitar XSS, no poner nunca el ID en la URL y limitar la duración de la sesión.

7.2. Fijación de sesión (session fixation)

El atacante no roba el ID: consigue que la víctima use uno que él ya conoce (por ejemplo, con un enlace que lo fija). Cuando la víctima inicia sesión, el atacante, que tiene el mismo ID, entra con ella.

Defensas:

  • session_regenerate_id(true) justo después de iniciar sesión (y en cualquier cambio de privilegios). El ID que conocía el atacante deja de valer. El true borra los datos asociados al ID antiguo.
  • use_strict_mode activado: PHP no acepta un ID que no haya generado él.

7.3. CSRF (Cross-Site Request Forgery)

La víctima, que ha iniciado sesión en tu aplicación, visita otra web. Esa web contiene un formulario oculto que se envía solo a tu aplicación (por ejemplo, para cambiar el correo de la cuenta). Como el navegador adjunta las cookies automáticamente, tu servidor recibe una petición auténtica de la víctima que ella no ha querido hacer.

Defensas:

  1. Cookie de sesión con SameSite=Lax: el navegador no la envía en peticiones POST que vienen de otro sitio.
  2. Un token anti-CSRF: un valor aleatorio guardado en la sesión que se incluye en cada formulario. La otra web no puede conocerlo.
<?php
/** Devuelve el token CSRF de la sesión; lo crea si no existe. */
function tokenCsrf(): string
{
    $_SESSION['csrf'] ??= bin2hex(random_bytes(32));
    return $_SESSION['csrf'];
}

/** Detiene la petición si el token enviado no coincide con el de la sesión. */
function comprobarCsrf(): void
{
    $enviado = $_POST['csrf'] ?? '';
    if (!is_string($enviado) || !hash_equals(tokenCsrf(), $enviado)) {
        http_response_code(400);
        exit('Petición no válida. Recarga la página e inténtalo de nuevo.');
    }
}

<form method="post">
    <input type="hidden" name="csrf" value="<?= tokenCsrf() ?>">
    <!-- resto de campos -->
</form>

Y en el procesamiento, lo primero: if ($_SERVER['REQUEST_METHOD'] === 'POST') { comprobarCsrf(); … }.

hash_equals() compara dos cadenas tardando siempre lo mismo, para que el tiempo de respuesta no dé pistas sobre cuántos caracteres coinciden.

7.4. Fuerza bruta

Un programa prueba miles de contraseñas contra un usuario. Defensas: exigir contraseñas robustas (como en la UT3, P09), hashes lentos (apartado 5) y limitar los intentos: tras varios fallos, bloquear durante unos minutos.

<?php
const MAX_INTENTOS = 5;
const BLOQUEO = 2 * 60;   // segundos

$bloqueadoHasta = $_SESSION['bloqueado_hasta'] ?? 0;
if (time() < $bloqueadoHasta) {
    $error = 'Demasiados intentos. Espera unos minutos.';
} else {
    // … comprobar las credenciales …
    // Si fallan:
    $_SESSION['intentos'] = ($_SESSION['intentos'] ?? 0) + 1;
    if ($_SESSION['intentos'] >= MAX_INTENTOS) {
        $_SESSION['bloqueado_hasta'] = time() + BLOQUEO;
        $_SESSION['intentos'] = 0;
    }
}

Limitación

Contar los intentos en la sesión sirve para aprender y frena a un usuario con el navegador, pero un atacante con curl simplemente no envía la cookie y obtiene una sesión nueva en cada intento. La solución real guarda los intentos por usuario y por IP en la base de datos (UT6).

8. HERRAMIENTAS DE PRUEBA Y DEPURACIÓN

Con cookies y sesiones aparecen errores que no se ven en la página: una cookie que no se guarda, una sesión que se pierde al cambiar de página, una redirección infinita. Estas herramientas te permiten ver lo que pasa (RA4 – CE f).

8.1. Herramientas del navegador

Ábrelas con F12 (o Ctrl+Shift+I; en macOS, Cmd+Option+I).

  • Red (Network): pulsa sobre una petición y mira las cabeceras. En la respuesta busca Set-Cookie y Location; en la petición, Cookie. Marca Conservar registro (Preserve log) para no perder las peticiones cuando hay una redirección.
  • Aplicación (Chrome) o Almacenamiento (Firefox) → Cookies: lista las cookies del sitio con todos sus atributos. Puedes editar el valor de una cookie o borrarla para comprobar cómo responde tu aplicación ante una cookie manipulada o ante una sesión perdida.
  • Ventana privada o de incógnito: empieza sin cookies. Úsala para probar como otro usuario sin cerrar tu sesión.

8.2. curl desde la terminal

curl envía peticiones sin el comportamiento «amable» del navegador: no sigue redirecciones si no se lo pides y te enseña la respuesta completa.

# -i muestra las cabeceras de la respuesta
curl -i http://localhost/ut04/privado.php

# -c guarda las cookies recibidas en un fichero; -b las envía
curl -i -c cookies.txt -d "usuario=ana&clave=Ana#2026" http://localhost/ut04/login.php
curl -i -b cookies.txt http://localhost/ut04/privado.php

# Enviar una cookie inventada
curl -i -b "rol=admin" http://localhost/ut04/admin.php

Con la primera orden comprobarás si tu página protegida tiene el exit después de la redirección: si ves el contenido privado debajo de la cabecera Location, no lo tiene. Postman, que usaste en la UT1, también guarda y envía cookies (pestaña Cookies de la respuesta).

8.3. Mostrar el estado mientras desarrollas

Un bloque temporal al final de la página te enseña qué hay en cada petición:

<?php if (getenv('APP_ENV') === 'desarrollo'): ?>
    <pre><?php
        echo 'ID de sesión: ', session_id(), "\n";
        echo '$_SESSION = '; print_r($_SESSION);
        echo '$_COOKIE = ';  print_r($_COOKIE);
    ?></pre>
<?php endif; ?>

Nunca en producción

Mostrar el ID de sesión o el contenido de la sesión en una página publicada es regalarle a cualquiera los datos para suplantar al usuario. Si usas este bloque, protégelo con una condición como la del ejemplo y bórralo antes de entregar.

8.4. Registro de errores

En desarrollo conviene ver todos los errores; en producción, ninguno en la página, pero todos en un fichero de registro:

Directiva Desarrollo Producción
error_reporting E_ALL E_ALL
display_errors On Off
log_errors On On

Con error_log() escribes tus propios mensajes en ese registro sin que el usuario los vea. Es útil para dejar rastro de eventos de seguridad:

<?php
error_log("Login fallido para el usuario '$login' desde " . $_SERVER['REMOTE_ADDR']);

Para saber dónde está el fichero: php -i | grep error_log. Si la directiva está vacía, los mensajes van al registro del servidor web. Para verlos en tiempo real: tail -f ruta/del/fichero.log.

8.5. Depuración paso a paso con Xdebug

Xdebug es una extensión de PHP que permite detener el script en una línea (punto de ruptura, breakpoint), avanzar instrucción a instrucción y ver el valor de todas las variables, incluidas $_SESSION, $_COOKIE y $_SERVER.

  1. Comprueba que está cargada: php -v debe mostrar with Xdebug. Si no aparece, actívala en la configuración de PHP de tu entorno (Herd o Lerd) o en php.ini.

  2. Configúrala en modo depuración:

    xdebug.mode = debug
xdebug.start_with_request = yes

  3. Conecta el editor:

    • VS Code: instala la extensión PHP Debug (de Xdebug), crea la configuración Listen for Xdebug (puerto 9003) y pulsa F5.
    • PhpStorm: pulsa el icono del teléfono Start Listening for PHP Debug Connections.
  4. Pon un punto de ruptura (clic a la izquierda del número de línea) y carga la página en el navegador. La ejecución se detiene y puedes inspeccionar las variables.

Cuándo usar cada herramienta

  • ¿La cookie llega o no llega? → Pestaña Red.
  • ¿Qué valor tiene ahora? → Aplicación/Almacenamiento.
  • ¿Por qué entra en ese if? → Xdebug.
  • ¿Está bien protegida la página? → curl.
  • ¿Qué pasó ayer a las 10:15? → Registro de errores.
